# 공식 커뮤니티 운영

공식 게시판은 공모 참여, 공부법 공유, 질문과 피드백으로 구성한다. 사용자 생성 커뮤니티와 학교 인증은 이번 버전에 포함하지 않는다. 과거 과목 그룹·채팅 스키마와 별개의 `community_*` 테이블이며 계정과 닉네임만 기존 Supabase 인증을 재사용한다.

## 접근과 배포

`20261021000000_community.sql`은 기존 `profiles`, `auth.users`, `bandal_account_deletions`, `bandal_account_write_guard()`가 적용된 프로젝트에 추가한다. 기존 마이그레이션을 수정하지 않는다. Edge Function이나 서비스 키를 새로 앱에 넣지 않는다.

- 앱은 계정이 소유한 main 프로세스 Supabase client로 `community_request(action_input,input)`를 호출한다. 콘텐츠를 읽으려면 로그인해야 한다. 인증 주체는 `auth.uid()`이며 클라이언트가 작성자·운영자 ID를 정할 수 없다.
- 웹과 로그아웃 앱은 `community_public_campaign()`만 호출한다. **공개된 캠페인 1개의 모집 요강과 일정, 상태만 반환**한다. 글, 댓글, 작성자, 신고, 공감한 사용자 목록은 반환하지 않는다. 미공개 캠페인은 `null`이다.
- `anon`과 `authenticated`의 모든 `community_*` 테이블 권한을 회수하고 RLS를 켠다. 내부 JSON 변환·트리거 함수도 두 역할의 직접 EXECUTE를 회수한다. Supabase의 기본 권한이 `authenticated`에 직접 부여되더라도 공개 RPC 두 개만 허용된다.
- 운영자는 신뢰된 SQL 경로에서 확인한 계정 UUID만 `community_operators(user_id)`에 등록한다. 앱에서 자신을 운영자로 만들 수 없다. 운영자만 고정·숨김·복원·댓글 숨김·신고 처리·공모 일정 관리·수상 및 개발 상태 변경을 할 수 있으며 감사 이력이 남는다.

```sql
-- 정확한 계정 UUID를 관리자 경로에서 확인한 뒤 실행한다.
insert into public.community_operators(user_id)
values ('확인한-운영자-UUID'::uuid)
on conflict do nothing;
```

## 공모전 공개

초기 캠페인은 `study-tools-2026`이며 **미공개, 모든 일정 미정**이다. 제목은 ‘반달에 있었으면 하는 공부 도구 공모전’이며 모집 요강을 미리 넣었다. 1등 10만 원·2등 5만 원, 실제 도움 40점·구체성 30점·구현 가능성 20점·독창성 10점의 심사 기준을 포함한다. 배포만으로 접수를 열지 않는다.

운영 화면에서 제목·설명·규칙·접수 시작·접수 마감·결과 발표 예정일을 확인하고 공개한다. 일정은 타임존을 가진 시각으로 저장한다. 접수 시작과 마감은 함께 지정해야 하고 시작 < 마감 ≤ 발표 예정일을 지킨다. 공개하려면 접수 시작·접수 마감·발표 예정일이 모두 지정되어야 한다. 접수 시작 이후에는 시작·마감 시각을 변경할 수 없다. 이미 접수한 사람의 기준이 바뀌지 않도록 규칙의 실질적인 변경도 운영자가 피해야 한다.

상태는 서버 시각으로 계산한다.

| 상태 | 조건 |
| --- | --- |
| `draft` | 미공개 |
| `upcoming` | 공개, 접수 시작 전 |
| `open` | 시작 이상, 마감 미만 |
| `judging` | 마감 이후, 결과 미공개 |
| `results` | 마감 이후, 운영자가 결과 공개 |
| `closed` | 공개된 캠페인을 운영자가 종료 |

결과 공개는 실제 마감 이후에만 가능하다. 1등·2등은 각각 캠페인당 한 게시물만 지정할 수 있으며 DB unique index가 동시에 선정하는 경우도 막는다. 기존 선정을 해제하고 다른 글에 다시 지정한다. 결과 공개 전 수상 필드는 운영자에게만 보인다. 개발 검토·개발 예정·개발 중·사용 가능·개발 보류는 수상과 독립적으로 관리한다. 상금 지급은 이 API에서 수행하지 않으며 수상자 연락과 지급 확인은 운영자가 별도로 처리한다.

## 제출, 심사본, 운영

공모 글은 대상 사용자·해결할 문제·사용 순서·구체적인 예시를 모두 작성해야 한다. 일반 글 제목은 120자, 본문은 10,000자(공모 글은 답변만으로 제출 가능), 공모 답변은 항목당 3,000자, 댓글은 3,000자까지다. 게시물과 댓글에는 파일 첨부가 없다. 원문은 일반 텍스트이며 UI에서 실행 가능한 HTML로 해석하지 않는다.

- 게시와 댓글 작성은 닉네임을 정한 계정만 가능하다. 작성자는 자신의 일반 글을 수정하고, 공모 글은 접수 중에만 수정한다. 운영자도 작성자 원문을 수정하는 API가 없다.
- 공모 글 생성·수정마다 `community_submission_snapshots`에 전체 제출 내용의 새 사본을 추가한다. 사본의 UPDATE와 DELETE는 트리거로 거부한다. 마감 후 원문 변경은 `community_posts` 트리거에서도 거부한다. 숨김·고정·개발 상태 변경은 심사본을 바꾸지 않는다. 가장 최근 접수 사본이 최종 심사본이다.
- 캠페인 행 잠금을 얻은 뒤 서버 시각을 검사한다. 마감 전에 도착했더라도 잠금 대기 중 마감이 지나면 새 제출을 받지 않는다. 앞서 성공한 요청의 동일 재시도는 마감 이후에도 최초 응답으로 복구한다.
- 게시물·댓글 작성에는 `requestId`가 필요하다. 계정과 요청 ID를 잠그고 요청 및 결과를 저장한다. 같은 ID와 같은 입력은 한 번만 적용하며 내용이 다른 재사용은 거부한다.
- 공감은 계정·게시물 PK와 원하는 활성 상태로 멱등 처리한다. 공감 수는 심사 참고이며 수상 자동 선정에 쓰지 않는다. 신고도 계정·대상당 한 번만 접수한다. 댓글 신고는 해당 게시물 소속인지 검사한다.
- 숨긴 글·댓글은 일반 회원 조회에서 제외하고 운영자는 검토·복원할 수 있다. 글 목록은 30개 단위로 고정 글 우선, 최신 순으로 조회한다. 운영 신고 목록은 미처리 우선 최근 200개를 보여준다.
- 계정당 변경 요청은 분당 60회로 제한한다. 재시도 영수증 조회는 새 변경으로 세지 않는다. 실패한 SQL 트랜잭션은 전체 롤백되므로 실패 시도 자체를 차단하는 방화벽으로 이 제한을 해석하지 않는다.

마감 심사본은 운영자의 신뢰된 SQL 경로에서 조회할 수 있다.

```sql
select distinct on (s.post_id)
  s.post_id, s.campaign_id, s.title, s.body, s.answers, s.captured_at
from public.community_submission_snapshots s
where s.campaign_id = 'study-tools-2026'
order by s.post_id, s.captured_at desc, s.id desc;
```

## 계정 삭제

기존 계정 삭제 잠금과 동일한 advisory lock을 사용하며 삭제 시작 후 새 커뮤니티 요청을 거부한다. 새 테이블도 기존 계정 삭제 쓰기 방지 트리거에 포함한다.

Auth 계정 삭제 시 글·댓글의 작성자 FK는 `NULL`이 되고 표시 이름은 `삭제된 계정`으로 바뀐다. 글이나 사본에 닉네임을 복제하지 않는다. 공감·신고·운영자 권한·요청 재시도 영수증·사용자별 제한 기록은 FK로 삭제된다. 제출 내용과 공모 심사본은 유지된다. 마감 후 작성자 연결만 제거하는 동작은 제출 내용 변경으로 보지 않으므로 계정 삭제를 막지 않는다. 게시글에 작성한 개인정보는 자동 식별하지 않으므로 공개 안내에서 개인 연락처를 적지 않도록 안내한다.

## 검증

```sh
node node_modules/vitest/vitest.mjs run tests/main/community/client.test.ts
node tests/backend/community/run-local.mjs
node node_modules/typescript/bin/tsc --noEmit -p tsconfig.node.json
```

DB 검사는 `pg_config --bindir`의 PostgreSQL 도구(없으면 PATH)를 사용해 고유 임시 디렉터리에 데이터베이스와 Unix socket을 만들고 종료 후 제거한다. 운영 DB·Supabase 프로젝트·기존 서버를 사용하지 않는다. Auth·프로필·계정 삭제 guard의 최소 fixture와 실제 마이그레이션을 적용하고 다음을 실제 PostgreSQL에서 검증한다.

- 테이블 및 내부 함수 권한, 익명 메타데이터 경계, 운영자·작성자 권한
- 요청/댓글 재시도, 타인 수정 거부, 공감·신고 중복, 숨김·복원 경로
- 마감 후 수정 잠금, 변경 불가 심사본, 결과 공개 전 수상 비노출, 개발 상태 분리
- 마감된 공모 글 작성자의 Auth 계정 삭제와 남는 심사본 익명화
- 동시 공감 8건, 같은 생성 요청 6건, 같은 수상 순위 경쟁, 잠금 대기 중 실제 마감 통과

이 검사는 로컬 PostgreSQL의 권한·트랜잭션을 검증하며 OAuth 브라우저 동작, 실제 운영자 계정 등록, 운영 Supabase RPC 공개 상태 또는 상금 지급을 확인한 결과가 아니다. 운영 배포 후 미공개 캠페인의 익명 응답 `null`, 콘텐츠 RPC의 비로그인 거부, 운영자 설정, 실제 계정의 게시→댓글→신고→검토 흐름을 별도로 확인한다.

## 2026-10-21 운영 확인

운영 Supabase 프로젝트에 마이그레이션을 적용했다. 승인받은 기존 계정 두 개의 UUID와 이메일을 재확인한 뒤 운영자로 등록했다. 아직 존재하지 않는 별도 운영 계정은 등록하지 않았다. `study-tools-2026`은 **미공개·접수 및 발표 시각 미정**으로 유지했다.

실제 HTTPS에서 익명 공개 캠페인 RPC는 `200 null`, 콘텐츠 RPC는 `401 / 42501`을 반환했다. 운영 PostgreSQL에서 실제 계정 UUID로 일반 회원·운영자 권한을 바꾸어 공모 답변만 제출, 동일 요청 재시도, 댓글·공감·신고, 권한 거부, 고정·댓글 숨김·개발 검토·신고 처리, 마감 이후 수정 거부와 심사본을 확인했다. 검증 전체를 한 트랜잭션에서 롤백했고 테스트 글과 테스트 캠페인이 각각 0개이며 기존 운영자 두 명과 비공개 공모 상태가 유지됐음을 확인했다. 이 검증은 실제 브라우저 OAuth 로그인 흐름을 실행한 결과는 아니다.

자료 마켓 API·webhook·cron 세 Edge Function을 종료 설정으로 다시 배포했다. 실제 HTTPS에서 마켓 context가 거래 비활성 및 종료 안내를 반환하고 새 주문은 `410 market_retired`로 차단됨을 확인했다. 위조 webhook과 비인증 cron 요청은 각각 `401`로 거부했다. 세 함수의 ACTIVE 배포 상태(API v7, webhook·cron v6)를 확인했다. 기존 거래 재조정 경로는 보존한다. 공모 접수 공개와 실제 상금 지급은 시작하지 않았다.

## 앱·웹 공개 확인

공식 커뮤니티는 [v0.87.4](https://github.com/seojune662/bandal/releases/tag/v0.87.4), 커밋 `123bcfb9ccd611da04f6bfa29d39cd260e93cc04`에 포함해 공개했다. 같은 커밋의 CI에서 관련 단위 검사 1,169개와 타입·실제 PostgreSQL 권한/동시성 검사가 통과했다. macOS·Windows 설치본에서는 각각 60개 검사가 통과했으며 커뮤니티 진입, 공모 안내의 일회 표시, 실패 후 동일 응모 복구, 댓글·공감·실제 앱 딥링크와 기존 구매본 가져오기 경로를 포함한다.

macOS 두 아키텍처의 서명·공증과 설치 파일·블록맵·업데이트 피드 12개 업로드의 무결성을 확인했다. 공개 URL 12개가 모두 비로그인 HTTP 200으로 응답했고, `latest-mac.yml`과 `latest.yml`의 버전 및 참조 파일이 `0.87.4` 공개 산출물과 일치했다.

[웹 공모 안내](https://bandal.io/community/contest)는 `bandal_web`의 `f2d671f`로 배포했고 영어 학습 예시를 `7185bdd`에서 앱과 통일했다. 운영 사이트에서 공개 캠페인 RPC가 실제 `200 null`을 반환하며 접수 버튼과 한국어·영어 홈 배너가 숨겨지는지 확인했다. 모바일 컴퓨터 참여 안내·복사 버튼, 데스크톱 앱 링크, 세 설치 파일 연결, 홈페이지 버전과 최종 앱 커밋의 체험판도 확인했다. 웹은 공개 메타데이터만 요청하며 게시글·댓글 API 요청이나 CSP 위반이 없었다.

로컬 웹 회귀 검사는 Chromium·WebKit의 공모 안내 30개, 기존 결제 화면 10개, 한국어·영어·모바일·데스크톱 체험판 8개가 통과했다. 자료 검색 CSS 수정 후에는 직접 영향을 받는 데스크톱 체험판 4개만 추가 확인했다. 운영 검증 스크립트의 다운로드 선택자·자동 칩 선택 가정을 수정한 뒤 실패했던 세 확인 항목만 재실행했다. 실제 OAuth 신규 로그인, 사용자 OS 권한 허용과 상금 지급은 수행하지 않았다. 공모는 미공개·일정 미정으로 유지한다.
